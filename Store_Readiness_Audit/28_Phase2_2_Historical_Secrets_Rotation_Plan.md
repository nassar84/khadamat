# تقرير 28: خطة تدقيق وتدوير الأسرار التاريخية المكشوفة في مستودع Git (Phase 2.2)

## 1. ملخص تنفيذي (Executive Summary)

أظهر التدقيق الأمني لسجل الالتزامات (Git Commit History) في المراحل السابقة وجود بيانات حساسة وأسرار اعتماد تاريخية كانت مضمنة في ملفات الإعدادات (`appsettings.json`, `google-services.json`, إلخ) قبل تطبيق نمط التجريد واستخدام متغيرات البيئة.

يقدم هذا التقرير **خطة تدوير شاملة ومحكمة عديمة التوقف (Zero-Downtime Secret Rotation Playbook)** لجميع الخدمات المتأثرة. 

> [!IMPORTANT]
> **التزام أمني صارم:**
> 1. لم يتم ولن يتم طباعة أو كشف أي قيم فعلية للأسرار أو المفاتيح داخل هذا التقرير أو في نصوص المخرجات.
> 2. لم يتم تغيير أي مفاتيح تشغيلية في بيئة الإنتاج الفعلية الحالية خلال هذه المرحلة حفاظاً على استمرارية الخدمة.
> 3. الهدف هو توفير خطة تنفيذية تفصيلية وجاهزة للتطبيق الفوري بالتنسيق مع مسؤولي البنية التحتية والأنظمة الخارجية.

## 3. خطة التدوير التنفيذية خطوة بخطوة (Zero-Downtime Rotation Plan)

### الخطوة 1: تدوير مفاتيح JWT (بدون انقطاع الجلسات)
بفضل نظام `JwtKeyManager` الذي تم تفعيله واختباره بنجاح:
1. توليد مفتاح سري جديد بطول 64 حرفاً مشفراً عشوائياً.
2. إضافة المفتاح الجديد في مصفوفة `JwtSettings:Keys` بالمعرّف `key-2026-v2` وحالة `active`.
3. نقل المفتاح التاريخي المكشوف إلى حالة `grace_period` بصلاحية 48 إلى 72 ساعة (تغطي مدة صلاحية التوكنات القديمة).
4. نشر التحديث على خوادم الـ WebAPI. كافة التوكنات الجديدة ستصدر بالمفتاح الجديد، بينما يستمر قبول التوكنات القديمة دون طرد أي مستخدم.
5. بعد انقضاء 72 ساعة، تحويل المفتاح القديم إلى حالة `retired` أو حذفه نهائياً.

### الخطوة 2: تدوير أسرار Firebase Admin SDK
1. الدخول إلى منصة Firebase Console $\rightarrow$ Project Settings $\rightarrow$ Service Accounts.
2. النقر على "Generate New Private Key" لتوليد مفتاح JSON جديد.
3. استبدال محتوى المفتاح في منصة الاستضافة (عبر Azure App Service Configuration أو متغيرات بيئة الـ Docker Container).
4. إعادة تشغيل خدمة الـ WebAPI والتأكد من إرسال إشعار تجريبي بنجاح عبر مسار الـ FCM.
5. العودة إلى كونسول Google Cloud Console وحذف المفتاح القديم (Revoke) لمنع استخدامه من أي جهة غير مصرح لها.

### الخطوة 3: تدوير بيانات اعتماد قاعدة البيانات (Database Credentials)
1. إنشاء مستخدم قاعدة بيانات جديد على خادم SQL Server أو Azure SQL بصلاحيات محددة فقط (`db_datareader`, `db_datawriter`, `db_ddladmin` عند الحاجة).
2. تشفير سلسلة الاتصال الجديدة وحقنها في بيئة الإنتاج السحابية.
3. التحقق من قدرة الـ WebAPI على تنفيذ عمليات القراءة والكتابة بالاعتماد الجديد.
4. تعطيل حساب المستخدم القديم (Disable Login) ومراقبة السجلات لمدة 24 ساعة، ثم حذفه نهائياً.

### الخطوة 4: تدوير أسرار Google & Facebook OAuth
1. الدخول إلى Google Cloud Console و Meta Developer Dashboard.
2. توليد `Client Secret` جديد لكل منهما مع الإبقاء المؤقت على الـ Client Secret السابق نشطاً إن أمكن.
3. تحديث الإعدادات في لوحة تحكم الخادم وإعادة التشغيل.
4. اختبار تسجيل الدخول الخارجي عبر الموبايل والويب.
5. إبطال الـ Client Secret القديم فور نجاح الاختبار.

### الخطوة 5: تدوير كلمة مرور خادم البريد (SMTP Credentials)
1. توليد App-Specific Password جديدة من حساب مزود البريد (Gmail / SendGrid / Microsoft 365).
2. تحديث المتغير `EmailSettings__Password` في الخادم.
3. إجراء اختبار إرسال رسالة تفعيل بريد إلكتروني.
4. إلغاء كلمة مرور التطبيق القديمة فوراً.

## 4. تطهير مستودع Git التاريخي (Repository Sanitization)

قبل تحويل المستودع إلى مستودع عام (Public) أو مشاركته مع أي طرف خارجي:
1. يوصى باستخدام أداة `git-filter-repo` المعتمدة رسمياً من مجتمع Git لإزالة الملفات الحساسة نهائياً من الـ Commit History:
```bash
git filter-repo --invert-paths --path-match "appsettings.json" --path-match "firebase-adminsdk*.json"
```
2. تفعيل فحص الالتزامات الآلي (Pre-commit hooks) باستخدام أدوات مثل `git-secrets` أو `Gitleaks` لمنع رفع أي بيانات حساسة مستقبلاً.
